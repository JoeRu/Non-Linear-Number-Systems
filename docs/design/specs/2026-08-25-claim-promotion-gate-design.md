The work that motivated a mutation registry was mostly not mutation work. Taking
`docs/risks.md` entry by entry:

| R-002 Narrative documents contain hand-copied numbers | documentation | Mitigated for the documents named in `PHASES` by `tests/test_figure_tags.py` and `tests/test_phase1_tables.py`. The entry states its own residual — a generated-but-untagged number — and states that no detector exists and none is planned |
| R-004 Lean proof references are validated by grepping text | documentation | A claim-validator matter. The entry records that the grep route validates none of the three Lean-citing claims today; each carries a checkable path alongside |

| R-003 The cross-check cannot detect a wrong place set | mitigated, not closed | Mitigated by a test — the hard-coded place list in `tests/test_fib.py` — which Plan A's CI now runs on every push and pull request. `docs/risks.md:181` records it as **mitigated**, with a live revisit trigger — a place set generated by a route other than `capfib.fib.places_up_to`, or a production `n_max` above 10^6, which the pinned list does not reach. What merged is the running of a test that already existed, not the entry's closure |

| R-010 The verifier and its inventory are editable by the pull request they gate | GitHub configuration | Closure is reading the inventory from the protected base ref, or CODEOWNERS per R-008 |

Five documentation problems the claim ledger already addresses, four process or
GitHub-configuration entries no test mechanism touches, and one mitigated by work
that has merged. Not one of the ten is closed by running a mutation. What a
mutation can do for the first group is protect the guards that mitigate those
entries — which is exactly what this design does, bounded to the claims those
guards stand behind.

**What is left is one thing.** A handful of guards protect the *numerical
evidence* behind claims the ledger has promoted to `verified-numeric` or
`theorem`. Those guards have been measured to be gutted with the suite still
green:

- **Certified T1 replaced by the constant `80.0`** — `5 failed, 286 passed`; and
  `pytest tests/test_saddle.py` on that tree is `3 passed`, so the module whose
  name suggests it covers the bound does not.
- **Every T3 `log_count` zeroed** — `4 failed, 287 passed`. Zero is a valid lower
  bound and a useless one; only an identity notices.
- **T5 weakened to `T3 + 0.01`** — `3 failed, 288 passed`. Every other T5 check is
  an inequality that a weaker bound satisfies more easily.
- **The break-index term dropped from the interval sum** — `1 failed, 290 passed`.
  The enclosure sits about `2.9e-27` **below** the true value while reporting a
  width of `4e-40`. The spec-5.5 agreement gate that both Phase 2 claims name in
  their `evidence` field compares at `RELATIVE_TOL = 1e-12`: fifteen orders of
  magnitude too coarse to see it. A "certified" upper bound below the value it
  certifies, and the named gate is structurally the thing that cannot see it.

No documentation discipline catches this class, because the claim looks
well-evidenced and the evidence is wrong. Three further measurements make that
concrete:

- Editing the literals inside a claim's `statement` — `rc-not-monotone` to
  "604441 … 395548 … 39.6%", `gate-local-slope` to "measures 0.618710" — gives
  **291 passed** and `scripts/check_claims.py` exit **0**. A claim's own numbers
  are compared to nothing.
- Corrupting `data/phase1_summary.json`'s census **and** re-recording the entry
  in `data/manifest.json` — which is exactly what every `scripts/run_phase*.py`
  does after writing an artifact — gives **291 passed**, `check_claims` exit
  **0**, with three claims now contradicted by their own evidence.
- Replacing `capfib/lower.py`'s T3 sum with `log_count = 0.0` leaves
  `check_claims` at `claims.yaml OK`. The validator never reads code, and no
  claim names a guard.

## 2. The rule

> **A claim may not be promoted to `verified-numeric` or `theorem` until the
> guard protecting its evidence has been observed to fail.**
>
> Observed means: the guard was run against a deliberately broken version of the
> computation or artifact it protects, in a scratch tree, and the named tests
> went red for the stated reason. A guard that has never been seen to fail is a
> claim about a test, which is the same species of claim as "the bound was
> verified".

### 2.1 Decisions taken

| # | Decision | Rationale |
|---|---|---|
| G1 | The unit is a **promoted claim**, not a test | The ledger is what the project publishes. Bounding by the suite is what produced a 1681-line spec for a small problem (§8) |
| G2 | The rule lives in the `claim-ledger` skill's promotion checklist, nowhere else | It is an observation a human makes at a moment in time. With no contract file, that observation leaves no artifact, so nothing else can host it (§2.2) |
| G3 | Mutations are **executed**, never declared | Every blind test in Phase 2 would have passed a declaration bar, because its author believed it worked |
| G4 | Mutations run against a scratch tree from `git archive`, not monkeypatch | The set includes file *absence*, which monkeypatch cannot express — and absence is defect 3 of the three `tests/conftest.py` records: `data/phase1_data.csv` gitignored, so twelve comparisons skipped on every clean clone |
| G5 | The verdict is the **failing node id set**, not the exit code | A non-zero exit is also produced by collection errors, import errors and timeouts. Red is not evidence of the right reason |
| G6 | Nothing runs in CI, and no status context is produced | Promotions are rare and deliberate. A per-push gate is the ceremony this design exists to avoid (§5.2) |

### 2.2 Where it lives

`.claude/skills/claim-ledger/SKILL.md`, section "Promoting a claim", as a
further item alongside the five that are already there. That file is where the
maintainer is already sent on every ledger edit, and the existing items set the
precedent that promotion discipline here is human-run.

Not in `scripts/check_claims.py`. Measured: it is a static reader — `hashlib`,
`json`, `re`, `sys`, `pathlib`, `yaml` — that starts no subprocess, imports no
pytest and runs nothing, so it cannot express "a mutation was run and the guard
failed" without a recorded artifact, which is the contract file this design
excludes. Timing is against it as well: it runs in the `tests` job on every push
and pull request, so a promotion rule placed there stops being a rule applied at
a promotion and becomes a permanent per-commit merge condition.

That argument is about *this* rule, which is an observation of a test outcome.
The statement-binding rule of §2.5 is statically decidable from files already in
the tree, which is exactly why the validator can host that one and cannot host
this one.

No new `CLAUDE.md` rule. The 2026-08-23 spec's §4 proposed one — rule 11, "a
guard you have not seen fail is not a guard", scoped to any test whose failure
would otherwise be invisible — and §9.4 ships it with Plan B, so it never
landed; `CLAUDE.md` carries ten rules today. This design keeps that sentence's
content and changes what it quantifies over: the claims the project has
promoted, not the suite. It adds no rule of its own.

### 2.3 What the rule does not apply to

`cited`, `heuristic`, `conjecture` and `open` claims are unaffected. The rule
binds at a **status change** into `verified-numeric` or `theorem`; it is not
retroactive machinery over the ledger, and §3 is a retrospective run once, not a
standing obligation.

Stated honestly, because the natural summary of this exemption is false of the
tree: it is **not** "most of the ledger". Measured, `theory/claims.yaml` holds 20
claims — 9 `verified-numeric`, 7 `theorem`, 2 `cited`
(`convention-duplicated-place`, `place-range`) and 2 `open`
(`saddle-correction-constant`, `secondary-term-constant`). Sixteen of twenty are
already promoted, and there is not one `conjecture` and not one `heuristic`
entry today. What the exemption actually covers is every entry that stays
unpromoted — including the two `open` ones, which carry the live research — plus
every future entry for as long as it stays unpromoted.

### 2.4 A claim whose evidence nothing guards

The rule is then unsatisfiable, and the claim is not promotable. There is no
third state to invent: nothing to mutate means nothing to observe.

`gate-local-slope` is that case today, already promoted. Measured: no test opens
`data/phase0_5_gate.csv` — the only two `phase0_5` hits under `tests/` are
strings inside synthetic fixtures in `tests/test_check_claims.py`. There is no
`tests/test_run_phase0_gate.py`;
`docs/phases/phase0_5/report.md` is not in `PHASES` and carries zero `{fig:}` tags;
there is no `data/phase0_5_figures.json`. Editing the document's headline
`0.518710` to `0.618710` gives **291 passed**, `check_claims` exit **0**.

This is the gate's first finding and it needs an action, not a note. The
recommendation is to write the missing guard — and to add the mutation that kills
it at the same time. **Not** by re-deriving the local slope from
`data/phase0_5_gate.csv`: `local_slope` is a finite difference of that same file's
`log_R_bound` column (`scripts/run_phase0_gate.py:42`), so such a test compares the
artifact to itself, which is the "consistency with an unverified root" pattern §7
disowns for the figure-tag chain. The guard that actually protects the claim
recomputes `capfib.saddle.log_R_bound` at the seven exponents. Measured, that
costs **4.18 s** in-suite for all seven — 2.13 s of it the 10^3200 point — and
reproduces every CSV value to the last digit, and an M1-style saddle mutation
kills it. The fallback, if no guard is written, is demotion to a status that
does not assert numerical verification. Leaving it promoted with nothing behind
it is the one option this design rules out.

### 2.5 The second half of the rule: bind the statement to the evidence

The rule above protects the *evidence*. It does nothing for the *statement*, and
the statement is what the project publishes. Measured on a scratch tree at HEAD:
editing `rc-not-monotone` to read 604441 increasing, 395548 decreasing and 39.6%
— while `data/phase1_summary.json` still holds 504441 and 495548 — gives
`claims.yaml OK`, exit 0, whole suite green. `scripts/check_claims.py` validates a
claim's *fields*, its artifact's *existence and SHA-256*, and `{claim:id}`
references in prose. The literals inside `statement:` are compared to nothing.

The hash check does not cover this and cannot, because the ordinary workflow
defeats it: corrupt `data/phase1_summary.json` **and** regenerate the manifest —
which every generator script does — and the run is fully green while
`data/phase1_figures.json` and the tagged documents still carry the old numbers.
Nothing compares the summary to the figures file, and nothing compares either to
the claim.

> **A claim may not be promoted to `verified-numeric` or `theorem` while any
> value its cited artifact provides appears in its statement untagged.**

**The check runs from the artifact to the statement, not the reverse.** A rule
demanding that every numeric literal carry a tag would be wrong. Measured,
fifteen of the sixteen promoted claims carry at least one numeric literal in
their statement, and most of those literals are structural — the `4` in
`1/(4 log φ)`, the `2` in `F_k²`, the `8` in `1/(8 log φ)`. Those are definitions,
not measurements, and no regex separates them from measured values. So the
checker starts from the evidence: for a claim citing an artifact with a figures
file, it renders each figure key at its recorded precision, finds every occurrence
of that rendering in the statement, and requires each occurrence to carry
`{fig:key}`. An untagged occurrence fails and names the key.

This reuses the mechanism the project already has rather than inventing one. The
tag grammar is `tests/test_figure_tags.py`'s `TAG` regex verbatim; the resolver
already renders a stored figure at its recorded precision and compares exact
strings; and the two shipped figures files have **no key collisions** (23 and 22
keys, measured), so a tag in `theory/claims.yaml` resolves unambiguously against
their union. What is new is only the direction: this is the
generated-but-untagged detector that `docs/risks.md` R-002 records as missing,
scoped to claim statements — which is where a wrong number does the most damage,
and a far smaller job than doing it for every document.

Two consequences the design accepts rather than hides:

- **`gate-local-slope` cannot be bound today**, because `data/phase0_5_gate.csv`
  has no figures file. That is the same gap §2.4 already names for its guard, and
  the same fix closes both: generating `data/phase0_5_figures.json` gives the
  claim both a guard and a binding. Until then it carries an exemption naming the
  missing file — not a silent pass.
- **A claim citing a Lean file has nothing to bind**, and §6 says so.

The two halves of the rule fail differently and that is deliberate. A guard that
was never seen to fail means *the evidence might be wrong*. An untagged value
means *the statement and the evidence might already disagree*.

#### 2.5.1 The check above does not work as written — measured, not argued

The review of 2026-08-25 implemented this algorithm literally over
`theory/claims.yaml` and ran it. Four results, each reproducible with a ~25-line
script that renders via `tests/test_figure_tags.py`'s `_format`, uses its `TAG`
regex verbatim, and runs `re.finditer` over each promoted claim's statement:

- **It misses the defect it was introduced to catch.** On the survivor tree whose
  `rc-not-monotone` statement reads 604441 / 395548 / 39.6%, the renderings to
  search for are `504441`, `495548` and `49.6` — occurrence counts **0, 0 and 0**.
  A statement that has *already* drifted contains no untagged occurrence, so it
  passes. The rule is vacuously satisfied by exactly the corruption of §2.5's own
  opening paragraph: it compels tags on values that are still correct, and never
  states the resolve-and-compare step that would catch a wrong one.
- **It fires on almost everything.** 54 untagged occurrences across 9 of the 16
  promoted claims. `min-count` renders `1` at precision 0, so every digit 1
  anywhere is an occurrence — 20 of the 54, including the `1` inside `1000000` in
  `block-extremal-n`. `residual-t-min` renders `10`, which matches inside
  `1000000`. No word-boundary or uniqueness rule was stated.
- **The no-collision justification does not transfer.** "23 and 22 keys, no key
  collisions" is true of key *names*; the check runs value → tag, and rendered
  *values* collide: `census-steps` and `n-max` both render `1000000`,
  `census-flat` and `flat-step-count` both render `11`, `ratio-at-nmax` (phase 1)
  and `ratio-nmax` (phase 2) both render `0.3582`. For those there is no
  determinate required tag. Verified against both figures files.
- **The artifact → figures-file mapping it assumes does not exist.**
  `data/manifest.json` is a flat file list carrying no such relation, and `PHASES`
  binds *documents* to figures files, not artifacts. Nothing in the tree says
  `chernoff-effective-verified`'s `data/phase2_bounds.csv` maps to
  `data/phase2_figures.json`.

So the sentence this section previously ended on — that the second half is
"measurable now, and the checker reports it now" — was false, and is withdrawn.
The half-rule needs a word-boundary and uniqueness rule and an explicit
resolve-and-compare step before it can be written at all.

**This is a decision for the maintainer, not one this document takes.** The
review recommends shipping the mutation rule alone (§2–§4, §5.1, §6) and demoting
this section to an open problem in §7, on the ground that a check firing 54 times
on 9 already-promoted claims is the shape a maintainer routes around — and that
routing around it would take the mutation rule bolted to it along too. The
alternative is to specify the missing rules and keep both halves. Until that is
decided, the operative instruction is the one already shipped in the
`claim-ledger` checklist: compare the statement's numbers against the artifact by
hand.

**Two kinds of link, and they are not equal.** A guard over the artifact field
the `evidence` names is one thing; a guard over the prose literals that report
the claim is another. For `rc-not-monotone` only the second exists: M9 kills
`test_every_tag_resolves_and_matches[phase1]`, the single node that compares
every tagged Phase 1 literal against `data/phase1_figures.json`, while editing
the census in `data/phase1_summary.json` leaves the suite green.
`flat-steps-end-early` and `completeness-empirical` share that node, but a
shared node is not a watched guard: M9 changes neither claim's key, so the
node goes red whether or not their literals are checked at all. Each needs a
mutation of its own figure key, observed to fail with that key in the
message, before it counts as reached. That node is a
consistency check between prose and a tracked artifact, not a recomputation —
measured: M2 zeroes T3 and every figure test stays green, because
`data/phase2_figures.json` still holds `17.774…`. The gate accepts it as the
guard for `rc-not-monotone` and this paragraph is why a reader should not read more
into it.

**Coverage, stated as the measurement and not as a target.** With the set in §4,
the rule is satisfiable for eight of the sixteen promoted claims (ten before
the PR #10 review removed the shared-node attributions; `flat-steps-end-early`
and `completeness-empirical` now wait on mutations of their own keys). Three more
(`sum-of-squares`, `gf-global-checksum`, `sc-monotone`) name their guard directly
in `evidence` and have a measured mutation held in reserve (§4.3). One
(`completeness-no-gaps`) is Lean and goes through §6. One
(`dp-gf-agree-to-nmax`) is unresolved. One (`gate-local-slope`) has no guard at
all. That is the finding the map exists to produce, and it is what the gate would
have surfaced at each of those promotions had it existed.

`scripts/mutate.py` does not exist today; nothing in the repository applies
mutations. It holds the entries below. Labels are the ones the measurement pass
used, so the record stays traceable — the gaps are the excluded candidates in
§4.2. Every anchor was re-counted against `df22d2c` and occurs exactly once in
the file's HEAD blob.

## 5. How it runs

### 5.1 The harness

One mutation, chosen because it guards the claim being promoted, applied to a
fresh scratch tree. Not the whole set: the rule is per claim, so the cost of a
promotion is one suite run — measured between 140 s and 252 s depending on
machine load — plus tree setup.

The requirements below are not stylistic; each was forced by a measurement.

1. **Scratch tree, from a committed candidate.** First require
   `git status --porcelain` to be empty: `git archive HEAD` exports the last
   commit, so a promotion whose evidence or guard is still staged or unstaged
   would otherwise be tested in its *previous* version and could be certified
   by a guard the candidate does not contain (PR #10 review). Then
   `git archive HEAD | tar -x` into a temporary directory. The
   repository is never edited — every measurement behind this spec ran that way
   and `git status --porcelain` was empty before and after each.
2. **Start the process inside the scratch tree.** `sys.path[0]` is the working
   directory, so cwd decides which `capfib` gets imported and it outranks
   `PYTHONPATH`. Measured both ways: cwd in the tree with no `PYTHONPATH` and no
   shim resolves `capfib.saddle` to the tree; cwd at the repository root with
   `PYTHONPATH=<tree>` resolves it to `/root/code/Non-Linear-Number-Systems`,
   and the M1 mutant then reports *5 passed* — the mutation survived, silently,
   which is the verdict this whole gate exists to prevent. Use `cd <tree>`, or
   `-P` / `PYTHONSAFEPATH`.

   The editable install is **not** the cause, and an earlier version of this
   step said it was. `__editable___capfib_0_1_0_finder` is appended to
   `sys.meta_path` *after* `PathFinder` — measured order
   `['BuiltinImporter', 'FrozenImporter', 'PathFinder', '_EditableFinder']` —
   so anything on `sys.path` beats it and the finder only fires when nothing
   else provides `capfib`. A `sitecustomize.py` shim that strips it is neither
   necessary nor sufficient: not necessary, because cwd in the tree already
   wins; not sufficient, because cwd at the repository root still loses.
3. **Prove provenance before running.** Import `capfib`, `capfib.fib`,
   `capfib.lower`, `capfib.saddle` and `capfib.interval` and assert every
   `__file__` lies inside the scratch tree; abort before pytest otherwise. All
   twelve runs of the measurement pass printed `PROVENANCE OK` before starting.
4. **Run the whole suite in the tree.** `-q -p no:cacheprovider -rfE`, with
   `--rootdir` and `-c <tree>/pyproject.toml` pointed at the mutant. Every kill
   recorded in §4 is a whole-suite result, and the "N failed, M passed" line is
   what those numbers mean.
5. **Baseline first, every time.** Run the unmutated scratch tree and require
   every target node to **pass**. Without it, a target that was already red
   before the mutation yields the same failing node set and the same pass count
   as a genuine kill (PR #10 review). This doubles the cost of a promotion to two
   suite runs; promotions are rare enough to pay it.
6. **The verdict is the node id set *and* the reason.** Exactly the recorded
   targets failed, nothing else did, and each target failed in the call phase
   with the recorded *Observed message* (§4.1) — for a figure mutation, the
   message must name the perturbed key. A mutation that makes the target raise
   an unrelated exception is not a kill. An exit code is not the verdict (G5).

### 5.2 Not in CI

This project's promotions are rare and deliberate. Measured: of the fourteen
commits that have touched `theory/claims.yaml`, four changed an existing
`status:` line; the rest added entries. A gate on every push would run a
mutation set on commits that touch no claim, which is the ceremony this design
exists instead of.

The same reasoning already stands in the register: R-007 records the refusal of a
blocking placeholder on a single-maintainer repository, because halting research
to protect against a maintainer ignoring a check they see on every run is the
worse trade.

### 5.3 The `mutations-full` context

`.github/required-checks.yml` names a `mutations-full` context with
`ships_in: plan-b`, and this design produces no status context at all — so the
inventory would name a producer that will never exist.

**Decision: the row is removed, in one change that also updates the test pinning
it and records the reason in `docs/risks.md` R-007.** Three things make that
different from the edit the file itself warns against:

- The warning is against deleting the entry *to make CI green* while the tier is
  still owed. The tier is not owed: this design replaces it.
- It cannot be done silently. Measured: deleting the entry alone turns
  `tests/test_required_contexts.py::test_the_tracked_inventory_parses_and_names_the_plan_b_context`
  red — exactly that node — so the deletion, the test change and the R-007 update
  land in one reviewable diff.
- It does not make CI green. R-007's delivery record names four problems in the
  `required-checks` run: no ruleset applies, and `tests`, `required-checks` and
  `mutations-full` are each not required. Removing the row removes one of the
  four. The verifier stays red until the branch rules are configured, which is
  repository configuration and not this design's business.

R-007's own closure clause is the second half of this: "Plan B shipping. Failing
that, a decision to accept the classes as open, recorded here rather than left
implicit." That is the decision, and the cost is real — the defect classes the
registry would have closed beyond this gate's scope stay open, and R-010's
exposure — the verifier and its inventory being editable by the pull request
they gate — stays dormant only because `required-checks` does not become
required. Dormant is not fixed.

## 6. Lean claims are different

`completeness-no-gaps` is guarded by Lean alone, and the Lean half of
`leading-constant` and `sandwich-bounds` with it. A Python mutation is
meaningless there, and the obvious substitute does not work:

**`lake build` does not catch a `sorry`.** Measured in a `cp -a` copy of `lean/`
with the entire proof body of `exists_numeral_of_le` replaced by `sorry`:

```
warning: ././././NonLinearNumberSystems/Completeness.lean:113:8: declaration uses 'sorry'
✔ [2510/2511] Built NonLinearNumberSystems
Build completed successfully.
lake_exit=0
```

**`#print axioms` does.** Unmutated:
`'NonLinearNumberSystems.exists_numeral_of_le' depends on axioms: [propext, Classical.choice, Quot.sound]`.
Mutated: the same line with `sorryAx` added. Note that `#print axioms` **also
exits 0 in both cases** — the verdict is in the output text, so the step must
grep for `sorryAx` rather than check an exit code.

A Lean-backed claim also has no figures file behind it, so §2.5's statement
binding has nothing to bind there and the axioms check carries the whole of its
evidence gate.

So the gate step for a Lean-backed promotion is: in a `cp -a` copy of `lean/`
(`git archive` cannot carry it — `lean/.lake` is 5.1 GB and gitignored), replace
the cited declaration's proof body with `sorry`, build, and run `#print axioms
<decl>`; the required observation is `sorryAx` appearing, and its absence in the
unmutated build.

Two facts the maintainer should carry into that step:

- **Nothing in the repository runs `#print axioms`.** Measured: every hit of
  `grep -rln "print axioms"` is prose describing the check — `docs/lean_setup.md`,
  `CLAUDE.md`, and the Phase 2 spec and plan under `docs/design/` and `docs/archive/` (and now
  this document). No workflow, no script, no test invokes it, and
  `tests/test_epistemic_staleness.py`'s `SCAN_GLOBS` never reach `lean/`.
- **`lake build` is off the merge path by construction.** It runs in
  `nightly.yml` only, by spec D12, pinned by
  `test_the_nightly_declares_its_schedule_and_still_builds_lean`. A Lean
  regression is unguarded on push and pull request by design, which is why the
  promotion step is the moment this check gets run at all.

Whether `lake build` would fail on a `sorry` under a stricter lakefile setting
was not tested; only the repository's current `lakefile.lean` was measured. The
step therefore pins `#print axioms` rather than relying on lake's warning
behaviour staying as it is.

## 7. What this does not do

- **It does not protect unpromoted claims.** The rule fires at a status change,
  so a guard behind a `conjecture` or `open` claim may be blind until the moment
  it is promoted. That is deliberate: the alternative is a standing obligation
  over the whole suite, which is §8's mistake.
- **No tamper-evidence.** No contract file, no fingerprint, no waiver ledger, no
  tiers, no required status context. The threat model is a solo maintainer's
  lapse of attention, not an adversary — R-008 states the same thing about the
  guard system generally, and this design does not pretend to more. Concretely:
  nothing observes whether the checklist item was done. This project has a
  written record of that enforcement failing before —
  `tests/test_figure_tags.py` calls a comment asking a later task to remember to
  flip a flag "precisely the enforcement that has already failed on this project
  four times", while `tests/conftest.py` enumerates three such defects; the
  discrepancy is unresolved and nothing here rests on the number.
- **The SHA-256 artifact check is tamper detection, not correctness.** It catches
  every silent artifact edit in §3, and it falls to a manifest rewrite, which is
  what the ordinary workflow performs: *291 passed*, `check_claims` exit 0, three
  claims contradicted by their own evidence.
- **The figure-tag chain is consistency with an unverified root.** It compares
  prose against the tracked figures artifact, and nothing ties that artifact back
  to the summary the numbers came from.
- **A claim's statement is bound only where its artifact has a figures file.**
  §2.5 *proposes* to close the general hole — an untagged value the cited
  artifact provides would fail promotion — but §2.5.1 measured that check as
  written missing an already-drifted statement, and the decision on it is open.
  Until it is made, the operative step is comparing the statement against the
  artifact by hand. Even once specified, the binding can only run where the
  values are published as figures. `data/phase0_5_gate.csv` has none, so `gate-local-slope`
  carries an exemption until `data/phase0_5_figures.json` exists. And the check
  is one-directional by design: it catches a *measured* value stated wrongly, not
  a number invented from nothing that the artifact never mentions. Distinguishing
  an invented literal from a structural constant is what §2.5 explains no regex
  can do.
- **T2 remains unguarded and uncoded.** §3.

Unresolved, and left unresolved rather than decided by assertion:

1. Whether M2's route to `sandwich-bounds` — through the T3 figure reported in
   the document its `evidence` field names, rather than through the field itself
   — is "the guard protecting its evidence". It is a real link and the thinnest
   of the code mutations.
2. Whether the small-N `dp`/`gf` cross-checks and the Phase 1 write gate are
   sufficient evidence for `dp-gf-agree-to-nmax`, whose claim is about
   `N <= 10^6` and whose recorded `crosscheck` string no test reads. This is a
   judgement for the maintainer; nothing measured settles it.
3. Which single claim M4 most tightly protects was not separated by a further
   mutation. The kill is measured; the attribution to two claims is by their
   `evidence` fields.
4. The three evidence artifacts no test reads (`phase0_5_gate.csv`,
   `phase2_bounds.csv`, `phase2_residual.csv`) are produced by `capfib.saddle`,
   `capfib.lower` and `capfib.interval`, which M1–M4 do mutate — but nothing
   re-derives the CSVs, so a kill there is a kill on the library, not on the
   published artifact.
5. Mutations were each measured alone in a fresh copy. Interference when applied
   in sequence — M2 then M3, which live in the same module — was not measured.
   The gate runs one at a time, which is why this has not been forced.
6. No per-test timing regression was checked, so a mutation that only slows the
   suite would not have been detected by any run behind this spec.
7. Whether a Lean mutation belongs in `scripts/mutate.py` at all. §6's step needs
   `lake build`, which the measurement pass did not attempt or time from a
   runner.

## 8. Supersession

This replaces `docs/superpowers/specs/2026-08-24-mutation-registry-design.md`,
written on branch `plan-b-registry` and never merged. It reached 1681 lines: a
registration schema, a coverage-is-equality rule, a marker checked in both
directions at function granularity, a workflow contract with parse and
normalization rules, a fingerprint, a waiver model with edge transitions, two
tiers, CI wiring and a new `CLAUDE.md` rule.

What it got wrong is one thing with many consequences: **it bounded the work by
the test suite rather than by the ledger.** 291 tests partitioned into 51
properties, each owed a marker and either a mutation or a counted exemption, is a
scope that generates its own apparatus — the fingerprint exists to protect the
registry, the waiver exists to protect the fingerprint, and the tiers exist
because running the whole set on every push costs too much. None of that serves the mathematics. Sixteen promoted claims is
a scope small enough that the mechanism fits in a checklist item and a script
with fewer entries than the ledger has promoted claims, and the entries are
earned by promotions rather than by tests.

The registry spec declared itself to supersede §3 and §9.6 of
`2026-08-23-defect-prevention-infrastructure-design.md`. That supersession lapses
with it. §3 — the mutation registry — stands on `main` as originally written and
remains unshipped, which is the state R-007 already records. §9.6 exists only on
`plan-b-registry`, added by the commit that seeded the registry from Plan A's
review history and corrected by the next one; it is dropped with the branch, and
nothing on `main` refers to it. What carries forward is the sentence from §4's
proposed rule 11 — a guard you have not seen fail is not a guard — now quantified
over the claims this project publishes rather than over every test it runs.
